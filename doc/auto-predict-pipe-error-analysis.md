后续已按用户授权实施稳定性修复，变更及验证状态见[修复说明](auto-predict-stability.md)。下文“未修改源码”等表述描述的是先前分析阶段。

分析日期：2026-10-20。依据用户粘贴日志、当前工作区源码，以及本地保留的2026-10-19日志归档。本次仅分析和新增文档，未修改预测业务代码、模型、数据或运行中的服务，未启动1000万组预测。

## 补充调查：Windows已记录TensorFlow原生层崩溃

用户进一步询问资源泄漏后，读取Windows应用程序事件日志，获得比Java管道错误更早的证据。下面结论更新原先“仅凭Java日志无法确定Python发生了什么”的范围，但尚不能解释TensorFlow内部为何非法访问内存。

| 两个Python进程启动时间 | 2026-10-19 20:30:07（Asia/Shanghai） |
| 崩溃事件时间 | 两个均为2026-10-19 20:37:28 |
| 进程ID | `0x2d038`、`0x6b08c` |

两进程同时启动、约7分钟后在相同模块和相同偏移崩溃，时间上与该次自动预测吻合。可以确定当时发生了TensorFlow原生层崩溃；没有原始请求与进程ID映射，不能进一步确定具体哪组输入或哪个TensorFlow算子触发。Windows故障记录时刻、错误报告生成时刻、Java读到EOF/写到断管的时刻可能不同，不应将Java日志时间当成最初崩溃时间。

`0xc0000005`不是“内存不足”的专用错误码，也不是Java IOException本身。它可能来自原生库缺陷、并发/生命周期问题、版本组合问题、内存损坏等；现有证据不能确定由泄漏导致。该次查询没有取得同一时间窗内资源耗尽检测器ID 2004的记录，这也不能反过来证明内存完全正常。

从崩溃路径对应的Python安装目录只读取包元数据，当前版本为：TensorFlow 2.21.0、Keras 3.15.1、NumPy 2.5.2、PyTorch 2.14.0、scikit-learn 1.9.0、XGBoost 3.4.1。它们是调查时的安装版本，不是已锁定的故障时环境快照。requirements仅规定最低版本，未锁定版本；目前没有验证这些版本之间不兼容，不能直接以降级或升级作为结论。

### 是否发现资源泄漏

**Python业务对象：未发现随单次预测次数增加的显式全局列表/字典积累路径。** 模型和历史只在启动加载，特征和请求结果为局部对象。Transformer使用`eval()`和`torch.no_grad()`，没有看到逐次保留反向传播计算图的代码。

**Python线程与TensorFlow：存在重点验证点，尚未证明泄漏。** `fuse_prediction`每次请求新建一个`ThreadPoolExecutor`；LSTM在其中调用Keras `model.predict(x, verbose=0)`。虽然with会在正常退出时等待并关闭线程池，但频繁创建销毁线程、在不断变化的工作线程中调用TensorFlow，可能暴露原生线程状态、数据管道或分配器的问题。需要用相同输入、模型和依赖对比“当前临时线程池/固定线程池”，观测线程、句柄和Private Bytes，而不是把“创建线程池”直接等同于“没有关闭线程池”。`predict()`本身的框架开销也不等于已经证实内存泄漏。

**Java侧：确认存在独立的索引清理缺失。** `PredictionCandidateCache`的`scoreIndex`是单例中的长期引用：

- `put`向分数对应Set添加号码key。
- `clear()`只执行`cache.invalidateAll()`，没有清空`scoreIndex`。
- 缓存淘汰回调只打印日志，也不删除索引key。
- 同一个key如果被更新为不同分数，旧分数桶里仍保留该key。
- `SmartSelectChain`结束时确实调用了这个不完整的`clear()`。

因此缓存数据已删除后，索引依然可持有不再有效的号码key和分数桶；跨日期/不同组合持续运行时可累积。主缓存上限实际是100,000,000条（日志写成10m），也不是按字节数限制。这是可以从代码确认的内存保留问题，但不等于证明它触发了TensorFlow访问违规；Java堆与Python地址空间不同，只会通过整机资源压力等间接相关。

此外，Java先生成1000万组列表和去重集合属于巨量内存占用；预测结果文件写入任务进入公共线程池，若写盘/数据库处理慢，异步待处理任务也可能积压。这两者应与“对象永远无法释放的泄漏”区分。

### 下一步怎样验证且保护原功能

先增加只读诊断：保留Python stderr尾部和退出码；按固定频率记录每个Python PID的已完成真实请求数、Private Bytes、工作集、线程数、句柄数，以及Java和整机内存。工作集单独上升不足以认定泄漏，框架预热和内存池可能升高后稳定；Private Bytes随请求持续增长且不平台化更值得怀疑，仍需对象/原生分配证据确认。

在独立进程中以固定号码、固定模型、固定依赖运行对照压力测试，先比较当前实现与固定工作线程实现的概率、reason和长期资源曲线。若再评估`model(x, training=False)`代替`predict()`，须另做输出一致性验证，不能假定完全等价。不要每次请求调用`clear_session()`，也不要关闭LSTM或减少融合子模型来掩盖问题，这些操作可能影响模型生命周期、吞吐或预测结果。

本轮仍未修改业务源码或依赖，没有声称已经修复崩溃。明确索引问题、连接恢复问题和TensorFlow原生崩溃应分别验证，不能修好其中一项就宣称全部解决。

## 结论与证据范围

直接故障是Java向Python子进程的标准输入管道写请求时，管道已经不可写，后续还出现读取响应得到EOF。不是双色球组合校验失败，也不能仅凭这条错误认定为数据库故障或内存泄漏。

已确认存在的放大链路：

1. Python连接发生I/O异常。
2. `InitPythonProcessServiceImpl.runInference`捕获异常，但在finally里仍无条件归还同一个连接。
3. `PythonConnectionPool`不检查健康、不剔除、不重建；后续请求继续借用失效连接，反复写入同一坏管道。
4. `runInference`返回null，Future没有异常，`whenComplete`将它交给成功回调。
5. 成功回调先递增完成计数，再发布结果事件，导致日志出现“执行到第……组，预测结果:null”。这不代表模型完成了这些预测。

用户贴出的片段包含244次“管道正在被关闭”和1次“Python服务连接已断开”，末尾21:49:02仍有任务报错。保留的滚动归档从20:56:33已出现坏管道和null结果；该归档开头便已处于失败阶段，无法据此定位真正的首次故障时刻。

仅凭最初提供的Java日志，无法确定Python最初为什么关闭输入/退出。Python异常输出被消费后直接丢弃，同时没有记录退出码和进程ID。后续Windows事件调查已证实该时段发生TensorFlow原生层崩溃，见上面的补充调查；崩溃内部诱因尚未确定，尤其不能直接归因为资源泄漏。

## 相关问题：需要单独处理，不能冒充本次首次断管原因

### Future超时不会回收Python工作

`orTimeout(2, MINUTES)`只能让Future超时完成，不会自动终止Python进程或解除其readLine。如果两个连接中一个长时间卡住，另一个已坏，后续任务可能集中借到坏连接并快速刷错；这个场景符合日志表现，但没有进程ID和请求时间线，暂时不能确认。

预测执行器有2个线程、长度3的队列，拒绝策略为`CallerRunsPolicy`。队列满时main线程也会直接执行预测，所以栈中出现main是预期的背压行为，本身不说明线程池失效。尤其当任务在提交线程直接执行时，`supplyAsync`可能先阻塞，后面的`orTimeout`尚未注册，2分钟限制也无法覆盖这段执行。

### autoPredict返回不代表所有任务结束

`autoPredict`提交预测任务后不等待全部Future完成。用户日志20:56:47开始进入后续“购买推荐”责任链，此后预测线程仍有报错。当前没有明确的任务排空屏障，因此推荐阶段可能早于全部预测结果就绪。

即使等待预测Future，也不能直接声称文件和进度已全部落地：事件监听器内部还有另一个`CompletableFuture.runAsync`负责文件写入及进度更新，其完成状态也需要纳入设计。

### 1000万组并非真正流式生成

`autoPredict`调用`generateNaturalRandom(10000000, consumer)`。回调重载内部先调用返回List的重载，生成1000万组并shuffle后才逐项消费，同时构造去重HashSet。这会造成很大的Java堆占用，且源码的“避免一次性囤大List”注释与实现不符。

这是确定存在的资源压力，但没有Java/Python内存曲线、OOM记录或退出码，不能据此断言Python本次被内存耗尽杀死。

### Python推理的资源开销

`predict.py`的`fuse_prediction`为每次融合请求新建线程池并在请求结束时关闭，LSTM分支调用Keras `predict`。在百万次请求规模下，这是需要压力测试的性能和资源风险；当前未见证明泄漏或原生崩溃的证据，不宜先改并发或模型调用来“碰运气修复”。普通Python Exception通常会被脚本捕获并生成JSON错误响应，也不必然导致进程退出。

### 进度与恢复语义

当前startIndex用来初始化计数并判断是否达到全空间总数，但随机生成入口每次仍重新抽1000万组，没有按该值恢复相同随机序列。这是已有行为，与本次断管不同。若修复期间顺带改成顺序枚举、减少组数或换随机算法，会改变候选集，应单独讨论，不能作为连接故障修复捎带修改。

## 保持预测功能的修改边界建议

建议按以下顺序实施，先取得首次故障证据，再修复失败路径。以下为建议，本次尚未改动源码：

1. **保留退出诊断。** 对每个进程记录PID、启动/退出时间、退出码；保留有界stderr尾部，失败时输出。stderr必须继续单独消费，不能合并到stdout，因为stdout用于逐行JSON协议。正常请求不逐行打印大量Python信息，避免新的日志压力。
2. **隔离失效连接。** 写失败、EOF和协议不同步后不得归还为健康连接；剔除并受控补建。重建失败要有明确失败及有限等待，不能仅删除连接后让take永久阻塞。记录具体连接ID，避免所有线程反复重建造成风暴。
3. **失败不能进入成功回调。** 请求仍不可执行时传播明确失败，且不发布成功事件、不增加成功计数。成功响应仍原样传给现有解析和落库逻辑；JSON错误响应的判定也要在明确协议后覆盖。
4. **受控恢复与超时。** 若自动重试，限定次数，只针对无状态推理请求；同一输入、同一模型、特征与参数保持一致。I/O超时必须真正解除阻塞并隔离旧连接，不能让旧响应混到下一请求。关闭逻辑必须能终止正在读的进程，避免先关闭阻塞中的BufferedReader而卡住。
5. **独立修复排空语义。** 明确自动预测返回时，哪些任务必须完成；保持队列有界，不为1000万任务累积1000万个Future。是否等待事件监听器内的写入，需要明确完成契约并验证后续推荐结果。

保持不变的正常业务路径应包括：`type=predict`、`model=second_fusion_model`、原红蓝球输入、当前和值/跨度/奇偶过滤、模型文件和融合公式、概率阈值、候选组合生成规则及正常结果的存储格式。失败任务计数和后续推荐触发时间的修正属于可观察行为变化，必须明确说明，不能承诺“任何行为完全不变”。

## 修改前后应验证的场景

- 正常JSON响应原样返回，同一组输入与模型输出不因Java连接修复而改变。
- 子进程正常退出、崩溃、写管道失败、读到EOF：坏连接不复用，不出现null成功事件，能记录退出证据。
- 子进程活着但不响应：实际请求超时且释放资源，不串包、不无限占用连接。
- 初始化失败和重建失败：有限等待，明确失败，不能无限阻塞或无限重试。
- 并发借还、关闭与借用竞争、全部连接失效、主线程CallerRuns执行：容量与关闭语义保持正确。
- 完成屏障覆盖正常任务和异常任务，并核对推荐阶段与异步持久化的先后关系。
- 固定输入的模型回归比较，加长时间运行的进程内存、线程数、连接恢复及成功/失败计数监测。

目前没有实施这些修改，也未声称已复现Python首次崩溃或已通过真实模型长时间压力测试。
